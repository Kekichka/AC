| Людина \ Суддя | pass | fail | unknown |

- **Пропускає погане (мій `fail` -> суддя `pass`):** **0** (найкритичніший дефект відсутній: жодна зламана зміна не проїде в main).
- **Марна робота (мій `pass` -> суддя `fail`):** **0** (суддя не відхиляє валідний код).
- **Де розійшлися:** обидва випадки розбіжності стосуються граничних ситуацій `unknown`: в одному випадку людина вагалася, а суддя дав pass; в іншому (відкладеному `c-20`) суддя поставив fail через частковий лог.

## 4. Одна ітерація рубрики
- **Що саме змінено:** За рекомендаціями Huynh та ін. (arXiv:2605.06283) додано конкретні приклади виводу для статусу `unknown` та чітке правило для `scope_respected` (читання виключно рядків `+++ b/...` у git diff).
- **Чого НЕ робилося:** Не додавалися складні багаторівневі підкритерії, оскільки ускладнення правил знижує стійкість оцінки LLM.

## 7. Рішення
- **Виміряна каппа на всіх випадках:** $\kappa = 0.833$ (на відкладених контрольних тестах: $\kappa = 0.714$).
- **РІШЕННЯ:** **Суддя тримає браму** як фінальний фільтр після детермінованих перевірок у CI (`npm run verify`).
- **Обґрунтування:** Дефект «пропускає погане» дорівнює 0 (нуль пропущених критичних помилок), а каппа перевищує 0.70 навіть на відкладених тестах.

## 8. Чесні межі
- 20 випадків — достатній мінімум курсу для виявлення зміщень рубрики, але не вичерпна статистична вибірка для промислового бенчмарку.
- Каппа порахована на конкретному кодовому корпусі репозиторію; на задачах іншого типу або стеку суддя може змінити профіль помилок.
- Суддя не виконує динамічного навантажувального тестування та перевіряє артефакт лише статично.
